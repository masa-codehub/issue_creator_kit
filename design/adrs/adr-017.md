# 概要 / Summary

[ADR-017] プロジェクト構成の TDA 準拠再定義と段階的移行:
システムのディレクトリ構造を TDA (Test Driven Architecture) に最適化された形に再定義し、既存の非 TDA なアーキテクチャおよび詳細設計資産を、この新構造へ段階的に移行・再構築する。

- **Status**: 承認済み (Approved)
- **Date**: 2026-03-28

## 状況 / Context

現在のプロジェクトには以下の技術的課題が存在する。

- **設計と実装の乖離**: 既存の `docs/` 配下のアーキテクチャ図やスペックが、最新の実装コードやエージェントの作業プロセス（`reqs/`）と物理的に切り離されており、SSOT（Single Source of Truth）として機能しにくい状態にある。
- **TDA プロセスの未確立**: 以前の設計資産は TDA（テスト駆動アーキテクチャ）の思想に基づいた「制約（Policy）」や「検証（Verification）」の概念が薄く、設計が実装を強制する力が弱い。
- **情報の混濁**: 検討中のドラフト、承認済みの仕様、および実装完了済みのアーカイブが明確に分離されておらず、エージェントが「今、何を根拠に動くべきか」を判断する際の認知負荷が高い。

これらを解決するため、プロジェクト全体を TDA サイクルへとシフトさせ、そのための「器」としてディレクトリ構造を抜本的に整理する必要がある。

## 想定ユースケース / Expected Use Case

1. **アーキテクチャの定義 (Arch Phase)**:
   - **アクター**: SYSTEM_ARCHITECT / TECHNICAL_DESIGNER
   - **ゴール**: 新機能の物理構造（L1-L3）を `design/architecture/` に定義し、同時にそれを監視する制約を `policies/architecture/` に配置することで、実装が設計から逸脱することを防ぐ。
2. **詳細設計と振る舞いの定義 (Spec Phase)**:
   - **アクター**: TECHNICAL_DESIGNER / BACKENDCODER
   - **ゴール**: `design/specs/behavior/` に Gherkin 形式で振る舞いを定義し、`tests/bdd/` でそれを実行可能にすることで、ビジネス要件を「生きた仕様」として実装に繋げる。
3. **段階的な資産移行**:
   - **アクター**: SYSTEM_ARCHITECT
   - **ゴール**: 既存の `docs/` 配下の古い設計を、Architecture フェーズから順番に TDA 準拠の形式で `reqs/design/_inbox` -> `_approved` へと引き上げ、最終的に `design/` 配下の新構造へアーカイブすることで、システム全体の整合性を回復する。

## 決定 / Decision

TDA の原則に基づき、プロジェクト構成を **「設計 (Intent)」「実装 (Reality)」「検証 (Evidence)」「作業 (Process)」** の 4 つの関心事で厳格に分離・再定義する。

### 1. 物理構造の再定義

以下のツリー構造を最終的な「理想の状態」として定義し、全ての資産をここへ集約する。

```text
/app/
├── design/                 # [SSOT Root] システムの「不変の正解」
│   ├── system-context.md   # システム全体の最上位設計
│   ├── adrs/               # [ARCHIVE] 実装完了済みのアーカイブ
│   ├── architecture/       # [MACRO] 階層化図面 (L1:Context, L2:Container, L3:Component)
│   └── specs/              # [DETAIL] 詳細仕様 (API, Data, Logic, Behavior, Interface)
│
├── policies/               # [CONSTRAINT] 設計の番人（静的テスト）
│   ├── architecture/       # アーキテクチャ・インフラ制約
│   └── specs/              # 詳細設計制約（API Linter, データ整合性等）
│
├── reqs/                   # [WORKSPACE] エージェントの作業領域
│   ├── design/
│   │   ├── _inbox/         # [DRAFT] 検討中のADR/DesignDoc
│   │   └── _approved/      # [ACTIVE SSOT] 承認済み・実装待ちのADR/DesignDoc
│   ├── context/
│   │   ├── context.md      # 対話ログ、判断背景（Interaction & Insights）
│   │   └── adr-{XXX}/      # 個別の作業文脈（target-context.md 等）
│   └── tasks/
│       └── adr-{XXX}/      # Issueドラフト
│
├── src/                    # [REALIZATION] クリーンアーキテクチャ実装
│   └── (app_root)/
│       ├── domain/   ├── usecase/   ├── infrastructure/   └── presentation/
│
└── tests/                  # [VERIFICATION] TDA準拠の検証
    ├── unit/   ├── integration/   ├── architecture/   └── bdd/
```

### 2. TDA への切り替えと移行プロセス

- **「設計から実装を駆動する」**: 今後は全ての変更を Architecture -> Specification -> Implementation の TDA サイクルで回す。
- **段階的移行**: 既存の `docs/` 資産は、本 ADR 合意後、Architecture レベルから順次 `reqs/design/_inbox` へコピーし、TDA の枠組みで再定義（制約やテストの追加）を行った上で、新構造へ移動させる。
- **ADR ライフサイクル**: `_inbox` (検討) -> `_approved` (実装中) -> `adrs/` (完了) の遷移を厳格に管理する。

## 検討した代替案 / Alternatives Considered

- **案A: `docs/` の名称変更のみ**: ディレクトリ名を変えるだけでは、検討過程と確定仕様の混在という「運用上の不透明性」を解決できないため却下。
- **案B: 一括リファクタリング**: 全てのファイルを一度に動かすと、既存の PR や作業中のタスクとの衝突が大きすぎる。Architecture フェーズから順を追って TDA サイクルに乗せていく「段階的移行」の方が安全かつ確実である。

## 結果 / Consequences

### メリット (Positive consequences)

- **トレーサビリティの向上**: 設計（Intent）とそれを検証する制約（Policy）がペアで管理されるため、設計の形骸化を防げる（TDAの実現）。
- **エージェントの認知負荷低減**: 進行中の正解（`_approved`）と過去の記録（`adrs/`）が分離されるため、AI が「今見るべき場所」を迷わない。
- **クリーンアーキテクチャの強制**: `src/` 配下の階層化により、依存性のルールがディレクトリ構造レベルで明示される。

### デメリット (Negative consequences)

- **運用の手間**: ファイルの移動（アーカイブ作業）という手動ステップが発生する。
- **移行期間の混在**: 全ての移行が終わるまでは、新旧のフォルダ（`docs/` と `design/`）が一時的に併存し、参照先を注意深く確認する必要がある。

## 検証基準 / Verification Criteria

- 全てのエージェントガイドライン（SYSTEM_ARCHITECT 等）が、この新構成と規律を反映した内容に更新されていること。
- `reqs/design/_approved/` に配置された ADR に基づき、`policies/` や `tests/architecture/` が正しく実装をガードできていること。
- 統合 PR の完了時に、対象 ADR が `_approved` から `design/adrs/` へ移動されていること。
